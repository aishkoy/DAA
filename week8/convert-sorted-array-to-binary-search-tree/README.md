Convert Sorted Array to Binary Search Tree

1. Problem
Дан массив nums, отсортированный по возрастанию. Нужно построить из него дерево поиска (BST), которое сбалансировано по высоте: у любого узла высоты левого и правого поддерева отличаются не больше чем на 1.

2. Approach
1) Если массив пустой, возвращаем null.
2) Берём средний элемент nums[mid], где mid = nums.length / 2, и делаем его корнем.
3) Все элементы левее середины меньше корня, поэтому из них строится левое поддерево. Все элементы правее больше, из них строится правое поддерево.
4) Через Arrays.copyOfRange копирую левую половину (от 0 до mid) и правую половину (от mid + 1 до конца) в новые массивы и рекурсивно вызываю ту же функцию для каждой.
5) Возвращаем корень.
Так как половины отличаются по размеру не больше чем на 1, дерево получается сбалансированным.

Tracing
nums = [-10, -3, 0, 5, 9]
Вызов [-10, -3, 0, 5, 9]: mid = 2, корень 0. Левая часть [-10, -3], правая [5, 9].
Вызов [-10, -3]: mid = 1, узел -3 (левый ребёнок 0). Левая часть [-10], правая [].
Вызов [-10]: mid = 0, узел -10 (левый ребёнок -3), обе части пустые.
Вызов []: возвращаем null (правый ребёнок -3).
Вызов [5, 9]: mid = 1, узел 9 (правый ребёнок 0). Левая часть [5], правая [].
Вызов [5]: узел 5 (левый ребёнок 9).
Результат: [0, -3, 9, -10, null, 5].
Для проверки делаю inorder-обход получившегося дерева: [-10, -3, 0, 5, 9], совпадает с исходным массивом, значит это правильное BST.

Challenges
Сначала хотела просто вставлять элементы по порядку в BST, как обычную вставку. Но массив отсортирован, поэтому каждый следующий элемент уходит вправо, и получается вырожденное дерево-линия высотой n, которое не сбалансировано. Поэтому корнем нужно брать середину, а не первый элемент.
Ответ не единственный: мой результат совпадает с выводом LeetCode [0, -3, 9, -10, null, 5], но там же сказано, что [0, -10, 5, null, -3, null, 9] тоже правильный. При чётной длине куска можно брать левую или правую середину, оба варианта сбалансированы и принимаются.
Проверяла на примере из LeetCode и на [1, 3]: mid = 1, корень 3, левый ребёнок 1.

3. Time Complexity
Time Complexity: O(n log n)

Каждый элемент становится узлом один раз, но на каждом вызове копируются половины массива. На первом уровне рекурсии копируется почти n элементов, на втором тоже почти n (две половины по n/2), и так на каждом уровне. Уровней log n, потому что массив каждый раз делится пополам. T(n) = 2T(n/2) + n, это O(n log n).

4. Space Complexity
Space Complexity: O(n), не считая самого дерева

Глубина рекурсии log n. Копии массивов на одном пути от корня вниз занимают n/2 + n/4 + ... что меньше n. Само дерево занимает O(n), но это ответ.

5. Reflection / Improvement
Лишняя работа здесь - копирование половин массива. Вместо копий можно передавать в рекурсивную функцию границы left и right текущего куска и брать середину как left + (right - left) / 2. Тогда на каждый вызов уходит O(1) работы, и сложность станет O(n) по времени, а дополнительная память - O(log n) только на стек рекурсии.
